# Input Understanding

Use this whenever the user provides messy notes, URLs, PDFs, transcripts, company situations, customer lists, or half-formed business ideas.

The goal is not to summarize. The goal is to convert raw input into a decision-grade work order.

## Intake Protocol

Extract these fields before analysis:

| Field | Question |
|---|---|
| User intent | What does the user actually want to decide, build, improve, or publish? |
| Object | What is being analyzed: market, company, customer, workflow, idea, account list, content, asset, or skill? |
| Audience | Who will use the output? Owner, solo operator, investor, customer, employee, reader, or partner? |
| Use moment | Is this for decision, research, sales, fundraising, turnaround, internal operation, content, or deck creation? |
| Timeframe | Is the question about today, next week, 90 days, annual planning, or long-term thesis? |
| Constraints | Cash, time, staffing, data, regulation, trust, geography, legacy systems, or channel access. |
| Evidence | What facts, documents, URLs, tables, or numbers are provided? |
| Missing data | What would materially change the answer if known? |
| Output | What should be produced: memo, scorecard, list, plan, dashboard, article, deck brief, or skill blueprint? |

## Understanding Ladder

Do not jump from input to polished output. Climb this ladder:

1. `Restate`: say what the input appears to be about.
2. `Decompose`: split it into entities, claims, numbers, causes, decisions, and constraints.
3. `Normalize`: turn messy text into structured facts, assumptions, and unknowns.
4. `Model`: identify the mechanism: buyer, workflow, cash, risk, distribution, or operations.
5. `Stress`: find contradictions, weak claims, missing numbers, and false positives.
6. `Route`: choose `radar`, `operator`, `assets`, or a combination.
7. `Output`: create the asset that helps the user act.

## Working Assumptions

If context is missing, proceed with explicit assumptions instead of blocking:

- `Assumption`: user wants practical business use, not academic theory.
- `Assumption`: output should be useful to a small team or solo operator unless otherwise stated.
- `Assumption`: if current facts matter, browse or label as not verified.

Ask the user only when a missing answer would change the direction materially.

## Deep Understanding Checks

Before producing the answer, ask:

- What is the real job-to-be-done behind the user's prompt?
- What would a naive summary miss?
- Which part is fact, which part is interpretation, and which part is aspiration?
- What is the hidden bottleneck: customer, data, cash, trust, workflow, distribution, or timing?
- What output would make the user able to move this forward today?

## Anti-Summary Rule

The user does not want a reservation-level summary. Avoid:

- restating the article or notes in nicer prose
- generic lists of trends
- frameworks that do not change a decision
- outputs without next action

Produce:

- causal structure
- decision logic
- prioritized options
- operating implications
- next experiment
- reusable asset
